# Document version integration through Scopevisio Teamwork

This opt-in project verifies the CenterDevice document version commands through the Scopevisio Teamwork bridge. It references `CompuMaster.Scopevisio.Teamwork` 2026.10.8 and `CompuMaster.Scopevisio.OpenApi` 2026.10.7 together with the local CenterDevice project. It does not verify direct CenterDevice OAuth or imply that every API 2.29 resource is forwarded by the bridge.

The project deliberately remains outside the solution and default workflows. Lifecycle, download and tag/lock tests each have explicit, nonparallel synchronous/asynchronous cases. A normal or explicitly filtered invocation without the environment opt-in skips before authorization. Build both frameworks first; select the relevant operation and execute `net8.0` and `net48` sequentially in one exclusive window.

Before running, coordinate the shared account with every relevant local session and all ecosystem repositories. Prevent new server workflows from starting for the entire preparation, execution and cleanup phase; a one-time check or identical concurrency names in different repositories is insufficient. Restore any temporarily disabled workflows to their recorded previous states after cleanup. The fixture's expiry guard records the operator's externally established lease; it does not establish an exclusive lock itself.

Set `CENTERDEVICE_TEAMWORK_LIVE=1` and `CENTERDEVICE_TEAMWORK_EXCLUSIVE_UNTIL_UTC` to the actual agreed UTC expiry only inside the test process. At least fifteen minutes must remain before writes, and five minutes before cleanup. Set credentials through `TEST_USERNAME`, `TEST_CUSTOMERNO`, and `TEST_PASSWORD`. On WKS08, existing `Scopevisio.Teamwork.Test` temporary credential caches can also be read directly; the fixture never writes or prints credentials.

```powershell
dotnet build CenterDevice.Rest.TeamworkIntegrationTests/CenterDevice.Rest.TeamworkIntegrationTests.csproj
dotnet test CenterDevice.Rest.TeamworkIntegrationTests/CenterDevice.Rest.TeamworkIntegrationTests.csproj -f net8.0 --no-build --filter "FullyQualifiedName~DocumentVersionBridgeTests"
dotnet test CenterDevice.Rest.TeamworkIntegrationTests/CenterDevice.Rest.TeamworkIntegrationTests.csproj -f net48 --no-build --filter "FullyQualifiedName~DocumentVersionBridgeTests"
```

Each case creates one unshared root collection named `ZZZ_UnitTests_CenterDevice_API229_Versions_<GUID>` and one uniquely named small text document. Tests check original and reverted payloads, preserved document identity/history, repeated revert creating another version, removal including the current version, selection of the largest remaining version, unavailable deleted versions, non-reused version numbers, repeated removal preserving state, rejection of deleting every remaining version, and pre-canceled commands leaving server state unchanged. Each mode exercises the corresponding synchronous or asynchronous new commands.

The temporary `CenterDevice.API229.Versions.owned-resources.json` ledger records only exact test resource identities and ownership. It records collection and upload intent before mutations and recovers only that scope after an interrupted run. Setup verifies absence; cleanup checks the actual CenterDevice owner separately from the Scopevisio authentication-context ID, rejects sharing or unexpected collection contents, removes the collection with its owned document, erases only recorded document IDs from the current user's trash, and verifies active and trash absence before removing the ledger. Keep a remaining ledger for recovery; never clear the server root or the entire trash. An independent bounded cleanup token runs in `finally` even after test failure. Failure and cleanup diagnostics are reported separately without emitting provider response bodies or authentication headers.

The extra trash client is test-only and follows API 2.29 sections 5.19.1 and 5.19.4 solely for complete owned-resource cleanup; it adds no public production SDK operations.

The lifecycle cases also verify typed version history before and after reverts/removals, including current-version identity, exact existing version numbers and per-version filename, size and timestamp. Regular and weekly workflows now run the separate isolated SDK regression project explicitly; the live project remains opt-in and outside automatic CI.

The `DownloadRepresentationsThroughTeamwork` cases verify current and historical fulltext, then upload a small valid PDF as a new version of the same owned document. They record actual PDF and preview-generation outcomes, inspect original standard/streamed ZIP contents and existing-PDF ZIP contents when the representation is ready, and verify cancellation. Only the tiny known ZIP fixture is buffered for archive inspection; production SDK downloads remain streaming.

A plain-text PDF conversion probe exposed a bridge limitation: after a bounded generation wait the bridge returned HTTP 200 without Content-Type rather than the manufacturer's generation/unsupported status. The SDK rejects that response as InvalidResponseDataException; it does not guess a 204 or 406. With an actual PDF fixture, PDF bytes and JPEG previews were ready; unsupported PDF-to-MP4 conversion returned a correctly classified HTTP 406. Actual ready PDF/preview results, pending generation, unsupported conversion and malformed bridge results must remain distinct in verification reports. The fixture logs only MIME/status diagnostics and owned-test outcomes, never provider response bodies, locations or authorization headers.


The TagAndLockCommandsThroughTeamwork cases verify selected/bulk tag additions/removals, exact failed-documents lists against an absence-verified missing ID, metadata lock-owner identity and selected/bulk lock/unlock. They use only the same owned document/collection scope. Independent finally cleanup removes only locks belonging to the actual test owner before deleting the document, and preserves both command and unlock-cleanup failures. The first live batch exposed red/RED duplicates; new SDK additions now apply the documented normalization before authorization, covered by a before-fix failing regression. Other roles and tenants are not inferred from this owning-account evidence.


The ConfiguredUploadsMetadataAndSearchThroughTeamwork cases exercise PR75–78 selected/current metadata, explicit document and version metadata/MIME, duplicate detection, version-independent extended-metadata set/unset and latest-version typed filtered/sorted search. Each mode uses one new unshared owned collection and an exact GUID filename, with upload intent and all confirmed IDs in the existing recovery ledger. Recovery covers an unexpected second created duplicate with that owned filename; it never erases unrelated duplicates. Full collection inventory must remain exactly one document after duplicate detection. A bounded 90-second read-only indexing wait distinguishes delayed search from immediately current metadata. No archive/email extraction, external recipients, ownership transfers, tenant settings or other-role/direct-OAuth acceptance is implied. Both frameworks compile and the no-opt-in gate must skip before authorization; actual remote evidence remains separate until the coordinated invocation occurs.

The OwnedResourceContractsThroughTeamwork cases cover merged PR81/85/87/89 with only fresh unshared owned collections and two GUID filenames. Upload intents and confirmed IDs use the existing recovery ledger; complete known inventory and filename absence are checked before each creation. Own tag visibility and timeline indexing waits are bounded, read-only, and lease-checked. Comments verify original HTML/actual creator/update/list/removal. Timeline checks explicit creator/document/date filters and one exclusive logical cursor step without inferring synchronization completeness. Deprecated original ZIP verifies the exact selected file/payload. Selected and bulk trash movement, restoration and direct selected/bulk erasure use only confirmed owned IDs, with active/trash absence checks. Independent finally cleanup also handles failures before those final checks.

These cases do not force or infer other-owner partial failure reasons, ready-PDF generation, normal/upload link permissions, global settings, external recipients, other roles or direct CenterDevice login. Successful detailed bulk requests with HTTP204 do not prove HTTP200 detailed-error behavior. No raw comments, event bodies, URLs, tokens or credentials are printed. Build both frameworks and prove the absent opt-in skips before authentication. Actual four-case execution requires a fresh coordinated exclusive automated window including setup/cleanup; preserve the human Test-Temp scope, restore workflows to their original states and explicitly release the window after verified ledger removal. Source readiness or skipped gates are not actual acceptance.
