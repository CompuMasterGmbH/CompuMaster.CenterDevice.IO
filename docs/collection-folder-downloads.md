# Collection and folder ZIP downloads

`CollectionRestClient.DownloadCollectionAsZip[Async]` downloads a visible collection's latest original document representations. Its `includeFolderStructure` option defaults to `false`, matching API 2.29 section 5.3.22. Set it to `true` to retain the folder structure. The server may rename duplicate filenames in an archive.

`FolderRestClient.DownloadFolderAsZip[Async]` downloads a visible folder's latest original document representations with folder structure, matching section 5.4.12. Its POST body contains only `action: download`; the folder endpoint has no folder-structure option.

Both methods return an unbuffered response-owned `Stream`. Dispose it even after partial reading. Cancellation reaches authorization, shared origin admission and HTTP I/O; cancellation after headers disposes the response and prevents subsequent reads. Archives are generated by the server and may have no content length. The SDK does not extract them or infer that every document is visible to the caller.

The shared download transport disables automatic redirects and transient replay, negotiates `application/zip`, and rejects unsuccessful status codes or unexpected media types while disposing the response. The existing one-time refresh for a recognized expired authorization response remains available. Resource identifiers are escaped as one path segment and rejected before authorization when missing or equal to `.` or `..`. Existing interfaces and download defaults are unchanged.

Isolated fixtures check exact POST contracts, sync/async behavior, encoded identifiers, response/body disposal, cancellation, errors and lazy handling of a synthetic 5 GiB stream without buffering. The shared transport also has actual loopback HTTP regression tests. These collection/folder endpoints have not yet received live Teamwork or direct CenterDevice verification; successful document ZIP tests do not establish that evidence.
