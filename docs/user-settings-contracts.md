# Own-user settings contracts

The additive `UserSettingsRestClient.GetUserSettingsDetails`/`Async` and `UpdateUserSettings`/`Async` methods cover API 2.29 sections 5.9.1 and 5.9.2. Existing getters, interfaces and models remain unchanged. Authentication context and explicitly selected own user ID are separate; `current` selects the token's user. The server enforces own-user access.

Read projections use copied individual `data` names and retain the default of all when omitted. Immutable results preserve missing/null versus explicit false, empty favorites and complete original/future metadata. Mutable configuration objects returned by properties are defensive copies; editing them cannot alter the result. Tenant-setting indications are read-only: true grants the respective action at that point in time; false retains default behavior, under which role/ownership can still permit an action. Missing values remain unknown.

Typed JSON configurations cover all documented writable settings: locale; both notification channels and ten email switches; default view; workflow confirmation/sharing/visibility; default collection; contrast; archived searches; search history; individual favorite lists; and fulltext/filter sorting. Original strings, empty values, explicit false and future fields are retained. Typed null setters omit fields; supplied known settings cannot use ambiguous JSON null instead of a complete setting. Complete JSON and nested selections are deeply copied before authorization/I/O.

Only provided top-level fields change. Supplied locale, workflow and sorting configurations must be complete; default view requires its view. Notification updates must select at least one channel, with that channel complete. Favorites are the explicit partial-update exception: one list changes only that list, and an empty list clears it. The client does not retrieve or fill missing configuration. Sort order is asc/desc and score is unsupported for filter-only sorting; other catalog/locale/resource validity is server-authoritative. Read projections do not impose write-completeness or reinterpret future catalog values.

Setting `UseSearchHistory` to false also clears all server-side search-history entries. The client adds no mutation replay or speculative recovery; cancellation cannot establish that no change occurred. PUT requires HTTP 204, GET requires HTTP 200, and failures do not become successful empty settings. Duplicate/trailing JSON and invalid known response shapes preserve an inner diagnostic. Request bodies never include read-only tenant-setting indications.

Isolated fixtures/private TCP loopback verify wire shapes, copy semantics, complete versus partial updates, null/false/empty choices, permissions metadata and native cancellation. No actual account settings or search history are changed by these tests. Own-user access, channel effects, module catalogs and real update/restoration require separate coordinated server acceptance in #20/#15; publication/default DMS adoption remain separate.
