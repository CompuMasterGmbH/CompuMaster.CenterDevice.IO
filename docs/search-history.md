# Explicit search-term history

`client.SearchHistory` implements API 2.29 sections 5.24.1–5.24.3 through synchronous and native asynchronous methods. The protocol tracks usage of a textual term, not a saved document-search query/filter object. Existing factories/interfaces/search defaults remain unchanged; document search does not automatically add history or update its count/timestamp.

`GetHistory[Async]` omits sort for the server's unspecified order or sends `most-recent-first` / `most-used-first` through `SearchHistorySort`. It preserves the server order and returns at most the first 500 entries for that sort. There is no paging/total/full-history contract. Disabled history returns an empty page too, so emptiness cannot establish the user's setting.

`AddTerm[Async]` explicitly records one usage. The server matches an existing term ignoring case, increments its count and updates its timestamp; otherwise it creates an entry with count 1. The original request text, including empty strings/whitespace, is sent unchanged for server validation. Returned original term casing, ID, Int64 usage count and exact ISO8601 timestamp text are retained. Explicit offsets expose `DateTimeOffset`; offset-free text receives no workstation timezone. The schema supplies no creator ID, so the authentication context is not substituted for ownership.

`RemoveEntries[Async]` snapshots a nonempty ID selection and always sends a JSON array. Even a selected literal `all` remains an array element. Only the distinct explicit `ClearHistory[Async]` method sends the string `all`, removing the caller's entire stored history. Whole clearing is not normal integration-test cleanup. Selected removal confirms success for entries already absent. All operations preserve disabled-history/creator visibility errors rather than treating them as empty success.

Successful responses must contain usable metadata, positive Int64 counts and distinct identities. Native cancellation reaches authorization/admission/HTTP; existing expired-token refresh and bounded GET retries remain. Adding usage is non-idempotent, so uncertain POST outcomes are never replayed, and no automatic document search/hidden iteration/settings update occurs.

Isolated tests cover sort omission, raw terms/case-insensitive use, large counts, exact date text/offsets, capped pages/read-only order, duplicate identities, selection snapshots, explicit clearing versus ID arrays, malformed success, disabled-history errors and cancellation. Public-factory TCP probes verify UTF-8/nested wire bodies, all operations and GET 503 retries versus POST without replay. They touch no actual account history or server. Real own-term usage/list/selected cleanup requires a new coordinated bridge window; account-wide clearing is not performed for ordinary acceptance. Post-merge matrix, publication and default DMS package adoption remain separate prerequisites.
