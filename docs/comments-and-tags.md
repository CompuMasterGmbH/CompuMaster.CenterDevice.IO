# Explicit document comments and deprecated visible tags

CommentsRestClient implements all five API 2.29 section 5.5 workflows with sync/native asynchronous forms: AddComment, UpdateComment, RemoveComment, GetComment and GetComments. CenterDeviceClientBase.Comments supplies the existing context/configuration/error handler/prefix without changing older groups or interfaces. Both original document and comment IDs are escaped independently as path segments. Text is nonnull but explicit empty/whitespace/formatting is forwarded unchanged for server validation, without HTML encoding, sanitization or trimming. The SDK does not turn null into an implicit clear or empty comment.

The server enforces visible-document access, creator-only editing/removal and guest visibility for latest-version comments. Creation is non-idempotent, and no mutation replay, permission inference, version association, author fallback or automatic recovery ID is introduced. PUT/DELETE expect 204, creation expects 201 and reads expect 200. Original configured error hooks and diagnostics remain intact. Cancellation reaches authorization and HTTP I/O; cancellation after sending does not establish that no comment was added or changed.

Immutable DocumentComment retains original creator/text/ISO date strings and future parsed JSON. Creation's identifier-only result leaves other fields unknown. Detailed reads require declared identity/author/text, preserve omitted/null dates and correlate a selected ID including equivalent UUID spelling. Complete list metadata retains server order, exact RawJson and future envelope fields without invented paging/sorting. Missing or malformed arrays and duplicate comment identities fail with inner diagnostics rather than becoming an empty inventory. Duplicate/trailing JSON is rejected. Parsed future fractions use Json.NET's bounded precision; complete list RawJson retains exact original spelling.

TagsRestClient implements the deprecated read-only GET /tags in section 5.10.1, exposed through CenterDeviceClientBase.Tags. Its methods are explicitly obsolete for new callers. VisibleTags retains original order/casing/duplicates, exact RawJson and future fields; no normalization, sorting or deduplication is added. It never changes tags. The manufacturer recommends SearchDocumentDetails with Rows = 0 and an explicit tags facet, without an additional filter or query, for new autocomplete workflows. No default search or hidden facet request is inserted by this legacy endpoint.

Isolated fixtures distinguish original wire shapes, selected identity, null versus empty/unknown metadata, actual HTTP errors, cancellation and published compatibility. Actual creator/guest enforcement, comment lifecycle and visible-tag/facet behavior require coordinated owned-resource verification and cleanup separately in #80/#15. No comment is posted to another person's document and no server access or publication is implied by isolated tests.
