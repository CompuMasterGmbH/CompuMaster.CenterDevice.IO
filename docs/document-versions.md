# Document version commands

This bounded part of [#17](https://github.com/CompuMasterGmbH/CompuMaster.CenterDevice.IO/issues/17) implements manufacturer API 2.29 sections 5.2.3 and 5.2.5, pages 38-41. The reference PDF is pinned by SHA256 in parent #15. The APIs remain unpublished until independent SDK review/merge, post-merge verification and explicit release approval. DMS integration remains in CompuMasterGmbH/CompuMaster.Dms#90.

`DocumentRestClient.RevertDocumentVersion` and `RevertDocumentVersionAsync` send `POST document/<selected-id>` with `action=revert` and a numeric `params.version`. The result is the existing `NewVersionUploadResponse`. A successful call creates a new highest/current version from the selected version's contents. It preserves the document ID, earlier versions and their numbers; it does not extract or reorder the source version. Repeating the command creates another new version, so do not retry an uncertain failure.

`RemoveDocumentVersions` and `RemoveDocumentVersionsAsync` send the separate `delete-versions` command to that same selected document path, with numeric `params.versions`. Inputs are snapshotted and enumerated once before authorization. This does not delete the whole document. At least one version must remain; the server selects the largest remaining version as current and does not reuse deleted numbers. There is no client-side history fetch or assumed current-version arithmetic.

Both commands require an admin, internal or external user. Revert requires visibility and, when create-new-version is locked, lock ownership. Version removal ordinarily requires document ownership; the tenant's document-deletion setting can allow removal from visible documents owned by others. Lock ownership can still restrict removal, and archived/trash documents cannot have versions removed. These decisions belong to the server; local role/metadata hints are not permission proof.

Both synchronous methods delegate to native asynchronous operations. Cancellation reaches authorization, admission and active execution. Pre-cancellation does not enumerate version selections, authorize or send. Cancellation after sending does not prove that the write was not committed. Existing execution can refresh a token once after a confirmed expired-token rejection; ambiguous writes are not automatically replayed. Original exceptions remain inner exceptions when existing response handlers wrap failures.

Existing public interfaces, methods, metadata/defaults and IO behavior are unchanged. These REST operations target the explicitly selected document ID; no DMS/IO operation or capability is silently upgraded. No production package version is changed.

Isolated validation uses captured requests and cancellable fake execution, with numeric 64-bit versions, selected user/document identity, synchronous delegation, single enumeration/snapshot, response validation, original exceptions, input rejection and active/pre-cancellation. A shared published-baseline fixture checks public/protected signatures and defaults. These checks do not verify actual version histories, lock/role enforcement, archive/trash restrictions or real server acceptance. Live verification needs an exclusive coordinated window and disposable, verified owned documents. Do not delete versions of permanent fixtures or unrelated documents to test these APIs.

Remaining #17 work includes PDF/MP4/fulltext/ZIP downloads and broader preview options, plus coordinated server verification and publication/integration. The complete issue remains open.
