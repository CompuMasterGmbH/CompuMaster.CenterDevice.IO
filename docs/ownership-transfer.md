# Explicit document and collection ownership

API 2.29 section 5.2.36 transfers selected document ownership through POST documents; section 5.3.23 transfers collection ownership through POST collection/{id}. Both use action transfer-ownership with params.new-owner; the documents command additionally sends params.documents. A single-document convenience method uses the same documents route with one exact document ID.

DocumentRestClient, DocumentsRestClient and CollectionRestClient expose additive synchronous/native async TransferOwnership forms. Selected document sequences are captured once before authorization; existing interfaces, getters, IDs, defaults and sharing metadata models remain unchanged. New owner input is a user ID, never inferred from a name or e-mail. HTTP 204 confirms the command; HTTP 200 is not a declared partial-success response for either route.

The server enforces caller/new-owner admin/internal/external roles. Document transfer requires ownership or a transfer-ownership tenant grant. Collection transfer requires collection ownership. The former owner retains direct sharing; document and version uploader information does not change. Document transfer is explicitly non-idempotent: repeating it can fail because the former owner no longer has transfer permission. No uncertain write or automatic compensation is added. Existing expired-token refresh remains inherited. Native cancellation cannot establish that the server made no change.

Isolated and actual private loopback transport fixtures verify route/body/identity snapshots/204/cancellation/errors/no write replay. They do not establish role/tenant permission behavior or actual returned metadata. Real acceptance needs a coordinated exclusive window and a verified secondary owner capable of returning ownership and cleaning up exact owned resources; ordinary tests must not transfer ownership of permanent/shared roots or unrelated content. Package publication/default DMS adoption remains separate.
