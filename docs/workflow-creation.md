# Direct workflow creation

API 2.29 section 5.20.1 is available through `Workflows.CreateWorkflow` and its native asynchronous counterpart. POST workflows sends direct top-level creation fields and confirms a 201 workflow identity. This is separate from template use, which posts action/data to workflow-template/id. The current server caller becomes the creator; no creator/template/name/action field is fabricated in direct creation.

`WorkflowCreationOptions` requires current type read/approval/metadata-form, an exact main document ID and explicit positive Int64 document version. `WorkflowAttachment` now has an additive documented public constructor for immutable exact attachment document/version selections; the existing read model and signatures remain intact. No current/latest version is inferred. Read and approval can include attachments; metadata-form rejects nonempty attachments before authorization. Null omits the attachment field, while an explicit empty sequence remains an empty array of no attachments. Order and distinct version selections of the same document are preserved without guessed deduplication or availability.

Administrators/internal/external users may create workflows for documents visible to them. Group membership resolves at creation, while participant limits and main/attachment visibility remain server-enforced. Metadata-form participants must have an administrator/internal/external role; the client does not infer these roles from identifiers. Users/groups and other sequences snapshot once before authorization, preserving original identifiers/order and explicit empty arrays.

Confirmation mode accepts one/all; metadata-form requires one or omission and a supplied completion-condition object. Current individual metadata fields use full user.strings/numbers/dates keys with a usable tail; optional default values remain exact strings, including decimal precision and ISO8601 timezone text. The server validates actual required document metadata and meaningful completion state. Empty conditions/arrays are not assigned an undocumented client minimum. Additional nested completion data remains original; direct creation does not claim the metadata-template resolution facility documented for template use.

Existing immutable WorkflowFinalizingAction builders provide all seven current finalizers with workflow-specific collection/folder/source-collection/source-folder keys. At most one action is currently allowed for each confirmed/rejected result; nonempty rejected actions require approval type. Construction and isolated tests perform no document operations; the server enforces visibility, source membership and actual execution. Empty action arrays remain explicit and null omits that result selection.

Creation and responses can send notification emails according to user settings. Automatic sharing true can share the main document and attachments with participants; false fails when participants cannot see any selected document. Null preserves omission: the direct-creation paragraph does not establish the template-specific true default, which the client therefore does not impose. Comment preserves original Unicode/newlines or empty text. Visibility defaults to participant and sharing removal to no through omission; explicit document visibility/on-completion removal retain their meaning for workflow-created main/attachment sharings. Creation can later cause finalizing actions and sharing removal and is non-idempotent.

Native cancellation reaches authorization, admission and HTTP I/O. Uncertain writes are not replayed. Success must confirm usable identity in the body; malformed/unexpected success and trailing JSON retain original inner causes. Returned Location is not followed or used to infer identity, so untrusted locations do not trigger additional requests. Existing interfaces, command/detail behavior and transport defaults remain unchanged; the promoted attachment constructor adds usable input construction and guards only shapes already validated on reads.

Isolated fixtures cover sync/native direct wire, required/default/false/empty fields, one-time sequence/nested snapshots, main/attachment versions, metadata-form attachment prohibition, exact defaults/finalizer keys, identity/status/role/visibility errors and cancellation. Actual public-factory loopback POST probes cover UTF-8, nested attachment JSON, ignored untrusted Location and 503 no-replay. Real creation roles, resolved participants, notifications, document/attachment sharing/unsharing and finalizing execution require coordinated exact-owned Teamwork acceptance and cleanup. Full current serialized matrix, explicit publication approval and downstream default adoption remain separate.
