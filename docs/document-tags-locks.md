# Document tag and lock commands

API 2.29 sections 5.2.27–34 are exposed through additive sync/native async AddTags/RemoveTags and AddLocks/RemoveLocks methods on DocumentRestClient and DocumentsRestClient. Existing AddLock/RemoveLock signatures, defaults and behavior are unchanged. All new methods snapshot sequences before authorization and accept cancellation; uncertain writes and partial failures are never automatically replayed. Cancellation does not establish that no changes were committed.

HTTP 204 returns DocumentCommandResult.AllSucceeded=true with an empty immutable FailedDocuments list. HTTP 200 must contain a nonempty failed-documents string array, retained in server spelling/order. Failed IDs must belong to the selected request; UUID canonicalization is recognized without changing the reported spelling. Malformed or foreign failure data throws InvalidResponseDataException with its original parser/validation cause. Transport success does not establish success for every selected document or grant permissions.

Tag additions trim whitespace, omit empty values and keep the first spelling of case-insensitive duplicates before authorization, as specified by the manufacturer. Even an all-ignored addition uses the server result rather than fabricating local success. Removals preserve supplied strings. A Teamwork probe attached within-batch red/RED duplicates before this correction; the normalization regression fails before the fix. Caller-owned sequences are enumerated once.

API 2.29 supports only the create-new-version lock; unsupported lock names fail clearly before authorization. Tag/lock addition requires admin/internal/external roles and visible eligible documents. The lock protects upload, rename and revert from other callers. The lock/document owner can unlock; admins can unlock a visible document. Server responses enforce these restrictions; the client does not infer rights from names or IDs.

Isolated cases cover every single/bulk action in sync/async modes, complete/partial results, immutable failure IDs, malformed/foreign IDs, canonical UUID spelling, snapshots/normalization, argument rejection before authorization, cancellation, preserved HTTP causes and legacy lock defaults. The opt-in bridge fixture checks the actual owned server state and exact partial failures against an absence-verified missing ID. Independent finally cleanup removes only test-owned locks before collection/document/trash teardown, preserving original and cleanup failures. Direct OAuth, other roles/tenants, publication and default DMS consumption remain separate acceptance.
