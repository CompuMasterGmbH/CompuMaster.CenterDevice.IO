# Filtered workflow lists

API 2.29 section 5.20.7 is available through `Workflows.GetWorkflows` and its native asynchronous counterpart, returning existing immutable `WorkflowDetails` in a read-only list. GET workflows is bodyless and returns the server-selected visible results without invented paging, totals, limits, complete tenant coverage or automatic follow-up requests.

`WorkflowQueryOptions` selects all seventeen documented fields: document-id, role, status, result, include-document-visibility, types, creators, responders, responded, creation-date-from/to, last-modified-date-from/to, responder-status, include-where-attachment, sort and order. Null omits a field; explicit false, empty text and empty sequences remain explicit. Strings preserve original text; types/creator/responder sequences are enumerated once before authorization and serialized as CSV in their original order, including duplicates. A selected CSV entry must be nonblank and contain no delimiter comma; an empty sequence sends an explicit empty CSV value rather than being omitted.

Include-document-visibility true requires a nonblank document-id and omitted role. False or omission considers participant visibility without granting access locally. Include-where-attachment true requires document-id and selects workflows where it is the main document or an attachment; false without a document is explicitly permitted because the manufacturer ignores it. These dependencies fail before authorization if violated. Participation, creator/responder role, current response state, document/attachment visibility and permissions remain server-authoritative.

Current role values are creator/responder, overall status and responder-status are started/completed, and result is rejected/confirmed. Responder status is derived by the server from overall state and whether the caller responded; the client does not infer it. The list section documents read/approval type filters while creation/detail also support metadata-form. Original additional textual choices remain server-validated; forwarding them does not establish metadata-form or future filter availability.

Creation/modification date lower bounds are inclusive and upper bounds exclusive. Original ISO8601 text retains timezone and precision without DateTime conversion or local range reordering. The server defaults to creation-date sort and ascending order through omission; current sort fields are creation-date/completion-date and orders asc/desc. Explicit selections remain original rather than being clamped, normalized or replaced with defaults.

Each returned object preserves the same role-dependent projection as selected workflow detail. Hidden/omitted/JSON-null lists, caller/all responses and creator-visible finalizers remain distinct from explicit empty data. Original identity, creator, document/attachment version, exact date text and complete future nested data remain immutable. Canonical repeated GUID workflow IDs, unusable identity, malformed list/detail shapes and unexpected trailing JSON fail with original inner causes. Server errors and unexpected successful statuses do not become fake empty lists. Existing native cancellation and safe bounded GET retry are retained; reading executes no workflow actions.

Isolated fixtures verify all seventeen fields, sync/native/default calls, one-time snapshots, original date/CSV/false/empty choices, documented dependencies, server-controlled additional strings, immutable role-dependent results, empty and 501-item uncapped responses, canonical duplicates/schema failures, original errors and cancellation. Four actual public-factory loopback HTTP probes verify the prefixed bodyless GET, escaped document/date/CSV queries, UTF-8 metadata and existing GET retries. Real filtering, date boundaries, order, roles and attachment/document visibility need separate coordinated exact-owned Teamwork acceptance and cleanup. Direct workflow creation including attachments, full current matrix, explicit publication approval and downstream adoption remain separate.
