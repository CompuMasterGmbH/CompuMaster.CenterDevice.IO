# Explicit configured document and version uploads

UploadConfiguredDocument and UploadConfiguredVersion add path/stream synchronous and native asynchronous forms for API 2.29 sections 5.2.1/.2. All historical methods, interfaces and document-date behavior remain unchanged. Optional title/author/original ISO date strings, writable extended metadata and require-valid-extended-metadata are copied before authorization or stream creation. Filename and measured size come from the method; attempts to supply them in optional metadata fail rather than silently overriding choices. Future metadata remains intact. Dates and decimal metadata remain strings without conversion; the common namespace remains read-only.

New-document actions expose explicit collections, string-or-array folders, sharing users/emails/groups, tags, locks, archive extraction, email storage/attachment/index choices and duplicate criteria. Null typed setters omit fields; false, empty objects and empty arrays remain distinct. No location/sharing/inheritance/processing/indexing/duplicate defaults are inserted. Known structural constraints, archive single-location combinations and documented invalid email combinations are validated before authorization. Omitted email choices remain omitted; their documented defaults are used only to reject invalid combinations. Future catalog strings and fields remain server-authoritative. New versions reject every supplied actions object, including an empty one.

MimeType is an optional copied document-part content type, separate from JSON metadata. Omission retains application/octet-stream. Original casing/parameters survive without local file-type detection. Invalid header syntax fails before opening streams or authorizing.

Uploads retain metadata-first multipart framing, chunked streaming, measured length and existing timeout/admission/native-cancellation/authorization behavior. Stream uploads reuse the length-inspection stream for transfer and own/dispose all returned streams on success, failure and cancellation. Path uploads use the existing asynchronous file-stream helper. Existing explicit token refresh can reopen content; no new replay of uncertain writes is added. Cancellation after sending does not establish whether a document or version was stored.

Immutable DocumentUploadResult retains exact RawJson, a created ID or original positive new-version integer text without width narrowing, original failed folder IDs and future action outcomes. Omitted failed-folder metadata remains unknown; an empty list remains known empty. A 201 upload can have folder failures without undoing document creation. Explicit duplicate detection accepts the documented 409 duplicate list as a separate outcome with no created ID; it does not select a preferred duplicate or resend content. Unrequested conflicts remain ordinary errors. Configured error hooks are honored before parsing. Invalid known responses retain inner diagnostics, duplicate/trailing JSON is rejected, and parsed fractional values have Json.NET's bounded precision while RawJson remains exact.

The server determines permissions, duplicate equivalence, normalized tags, applicable locks, supported file types and metadata templates. Duplicate equality includes MD5/size, optional filename/owner checks, version count, comments/locks/tags/metadata/link and cross-owner visibility/sharing criteria; the SDK never evaluates or guesses it locally. Only the first folder in a collection is used by the server. Archive extraction can delete the uploaded archive and create additional collections/folders/files; email processing can omit the email or create attachments. Other actions can apply to extracted files. A stored upload is downloadable but indexing, preview generation and extraction are asynchronous, so 201 does not prove their completion. Live processing/recipient/template/role acceptance requires a coordinated owned-resource fixture with verified cleanup, separate from isolated HTTP/stream evidence.
